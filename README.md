# Business Entity Resolution

## 1. Overview

This project solves the Business Entity Resolution Challenge using a multi-stage pipeline:

1. Data preprocessing and normalization
2. Candidate generation (blocking)
3. Feature engineering
4. LightGBM model training
5. Candidate scoring and final matching
6. Generation of submission files

The goal is to identify which Source 2 and Source 3 records correspond to each Source 1 business entity.

Source 1 is treated as the reference entity set. A Source 1 entity may have zero, one, or multiple matching entities in Source 2 and Source 3.

## 5. Pipeline

### Step 1: Preprocessing

Run:

```bash
python src/preprocessing.py
```

This step cleans and normalizes the entity fields used for matching.

The preprocessing includes operations such as:

* text normalization
* Unicode normalization
* lowercasing
* whitespace normalization
* punctuation handling
* compact representations
* transliteration where applicable
* address normalization
* country normalization
* missing-value handling

The cleaned data is used by the blocking and feature-engineering stages.

---

### Step 2: Training Blocking

Run:

```bash
python src/blocking_train.py
```

This generates candidate pairs between Source 1 and Source 2/Source 3.

Blocking reduces the number of comparisons that need to be evaluated by the matching model.

Only candidate pairs generated by the blocking stage are passed to feature engineering and model training.

---

### Step 3: Test Blocking

Run:

```bash
python src/blocking_test.py
```

This generates the candidate set for the test data.

The resulting candidate set is the set of Source 2/Source 3 records considered as possible matches for each Source 1 record.

These candidates are later used to generate:

```text
output/candidate_pairs.tsv
```

---

### Step 4: Feature Engineering

Run:

```bash
python src/feature_engineering.py
```

Features are generated for each Source 1–candidate pair.

The feature set includes name, address, country, exact-match, character-level and structural similarity features.

Examples include:

* exact name match
* compact name exact match
* transliterated name exact match
* Jaro-Winkler name similarity
* transliterated Jaro-Winkler similarity
* name containment
* name prefix/suffix features
* name script mismatch
* exact address match
* compact address match
* transliterated address match
* Jaro-Winkler address similarity
* address containment
* address prefix/suffix features
* house-number match
* postal-code match
* country match
* string length features
* missing-value indicators

The resulting feature data is stored in Parquet format for efficient processing.

---

### Step 5: Model Training

Run:

```bash
python src/train_model.py
```

The model is a binary LightGBM classifier.

For each candidate pair:

```text
label = 1
```

indicates that the candidate is a true match, while

```text
label = 0
```

indicates that the candidate is not a match.

The trained model is saved for test inference.

---

### Step 6: Test Prediction

Run:

```bash
python src/predict.py
```

The prediction stage:

1. Loads the trained LightGBM model.
2. Reads the test candidate features.
3. Generates a match score for each candidate pair.
4. Applies the selected matching threshold.
5. Groups predictions by Source 1 entity.
6. Produces the final matching output.
7. Produces the candidate-pair output.

The two required files are written to:

```text
output/matching_results.tsv
output/candidate_pairs.tsv
```

---

## 6. Output Files

### matching_results.tsv

This is the final submission file used for leaderboard evaluation.

It contains exactly two columns:

```text
source1_entity_id    matched_entity_ids
```

Example:

```text
source1_entity_id    matched_entity_ids
S1-00001             S2-00047,S2-00193,S3-00812
S1-00002             S3-00004
S1-00003
```

Every Source 1 entity appears exactly once.

If no matching Source 2 or Source 3 entity is predicted, the `matched_entity_ids` field is empty.

---

### candidate_pairs.tsv

This file contains the candidate set generated by blocking.

It contains:

```text
source1_entity_id    candidate_entity_ids
```

Example:

```text
source1_entity_id    candidate_entity_ids
S1-00001             S2-00012,S2-00047,S2-00193,S3-00812
S1-00002             S3-00004,S3-00019
```

The final predicted matches are a subset of these candidates.

## 7. Reproducing the Submission

From the `business_entity_resolution` directory, run the stages in order:

```bash
python src/preprocessing.py
python src/blocking_train.py
python src/blocking_test.py
python src/feature_engineering.py
python src/train_model.py
python src/predict.py
```

After successful execution:

```text
output/
├── matching_results.tsv
└── candidate_pairs.tsv
```

will contain the final submission files.

## 8. Validation

The submission can be validated using the challenge-provided validation script:

```bash
python utils/validate_submission.py \
    --matching output/matching_results.tsv \
    --candidate output/candidate_pairs.tsv \
    --test-dir dataset/test
```

The validation checks the required output structure and consistency with the test entities.

---

## 10. Important Notes

* Source 1 is the reference entity set.
* Matching is performed against Source 2 and Source 3.
* Blocking is performed before feature engineering to reduce the number of comparisons.
* The final model is applied only to generated candidate pairs.
* `candidate_pairs.tsv` represents the candidate set used for final test inference.
* `matching_results.tsv` contains the final predicted matches.
* Source 1 entities with no predicted matches are retained in `matching_results.tsv` with an empty `matched_entity_ids` field.
* Both output files must be generated from the provided test data and the pipeline code.
